## Findings

**Paid 503 after a disconnect.** The first request after each dropped stream was paid and
then refused with 503. Discovery still advertised the slot while the runtime finished the
cancelled request. A recovery poll after a discovery refresh saw zero capacity and was
rejected before payment. Back-to-back traffic on a single-slot runner hits the same window.
The tracker already lists cached capacity. This run adds its cost: one wasted ticket per
occurrence. A runtime restart produced one paid 502 before discovery dropped the runner,
which Core recorded as `uncertain`.

**Payment errors look like backend errors.** During one three-second window, the node
failed four payment challenges and then rejected one received payment. The gateway returned
the first four as unpaid 502s and the last as a paid 400. Redemption failed in the same
window, which points to the chain RPC, but the node logs carry no further detail. Native
routes forward these statuses unchanged, so a client cannot tell a payment-layer 400 from a
vLLM validation error.

**Suite assumptions that native vLLM does not meet.** vLLM returns `finish_reason: "stop"`
for a forced named tool call; the gateway returns the same bytes. Both repository suites
require `tool_calls`. With thinking enabled by default, Qwen3 also returns an Anthropic
`thinking` block, which the accounting suite reads as a tool call. The accounting run used a
local copy with the forced-tool cases skipped and only `tool_use` blocks read as calls;
every accounting assertion was unchanged.

**Winning tickets.** The test node uses a win probability near one half. It accepted 171
tickets, 87 of them winning. One was redeemed on-chain and succeeded. It used 191,870 gas at
0.02 gwei, about 0.0000038 ETH: 9.6 times the 0.0000004 ETH face value. The node was then
stopped, leaving 86 tickets unredeemed in its volume. Those upstream example values are no
longer rendered: `deploy/livepeer/orchestrator/render-config.py` now refuses a face value
below its capped redemption gas cost.
